# Data Model: Season & Postseason Data as Plain JS/TS Modules

This feature changes *how* the existing entities are stored and loaded, not their shape. The
field-level shape already exists today as the `SeasonData` type (`src/Chart/types.ts`) and the
postseason bracket shape produced by `scripts/scrape-playoffs.mjs`; both are restated here for
traceability back to the spec's Key Entities, plus the one new entity (the generated barrel) that
the loading-mechanism change introduces.

**Amendment (2026-10-12)**: Both entities below were originally specified as `.ts`/`.js` source
modules; that storage-format change was reversed after review (see `research.md` Decision 2,
amended). Both are plain JSON again, unchanged from before this feature. Only the Season Index
entity (still new) is unchanged by the amendment.

## Season Ranking Record

One JSON file per season — format unchanged by this feature.

**File**: `src/data/seasons/<season>.json` (e.g. `src/data/seasons/2024-25.json`)

**Shape** (unchanged `SeasonData`):

| Field | Type | Notes |
|---|---|---|
| `season` | `string` | e.g. `"2024-25"` |
| `maxWeek` | `number` | highest week number with data this season |
| `rankings` | `Record<TeamSlug, WeekRanking[]>` | per-team weekly entries |
| `playoffs` | `Record<TeamSlug, PlayoffStage>` \| `undefined` | only present for seasons with postseason data; per-team furthest stage reached |

`WeekRanking` and `PlayoffStage` are unchanged (`src/Chart/types.ts`).

**Validation rules**:
- `rankings` keys MUST be valid team slugs (`src/Chart/teams.ts`).
- Every `WeekRanking.week` MUST be `<= maxWeek`.
- `playoffs` keys, when present, MUST be a subset of `rankings` keys (a team can't have a
  postseason stage without season rankings).
- These are enforced only partially by the type checker now: the Season Index's `as SeasonData`
  cast (see below) still catches a structurally missing field (e.g. no `maxWeek`), but not an
  invalid `PlayoffStage` string value — see `research.md` Decision 2 (amended) for why.

**Generated by**: `scripts/build-rankings.mjs` via `JSON.stringify(output)` — unchanged from
before this feature.

## Postseason Result

The bracket of rounds/series for one postseason, keyed by season, all seasons in one file —
format unchanged by this feature.

**File**: `data/playoffs.json`

**Shape** (unchanged):

| Field | Type | Notes |
|---|---|---|
| *(top-level key)* | `string` (season) | e.g. `"2017-18"` |
| `source` | `string` | URL the bracket was scraped from |
| `champion` | `TeamSlug` | |
| `runnerUp` | `TeamSlug` | |
| `rounds` | `{ round: PlayoffStage; series: { teams: TeamSlug[]; winner: TeamSlug }[] }[]` | |

**Generated by**: `scripts/scrape-playoffs.mjs` via `JSON.stringify(results, null, 2)` —
unchanged from before this feature.

**Consumed by**: `scripts/build-rankings.mjs`, which reads it via `JSON.parse(readFileSync(...))`
(unchanged — this read was always synchronous) and reduces each season's bracket into the
`playoffs` field of the corresponding Season Ranking Record (unchanged reduction logic).

## Season Index (new)

A generated barrel that lets the app reach every Season Ranking Record through one static import
instead of a glob. This entity doesn't exist today (the app currently discovers season files via
`import.meta.glob`); it's introduced here to satisfy FR-003/FR-004 without hand-maintaining an
import list.

**File**: `src/data/seasons/index.ts`

**Shape**: a statically-imported, already-populated map from season string to its `SeasonData`,
plus the derived, sorted list of season strings the UI already computes today (newest first):

| Export | Type | Notes |
|---|---|---|
| `seasonData` | `Record<string, SeasonData>` | keyed by season string, one entry per `.json` file in `src/data/seasons/`, each cast `as SeasonData` on import (research.md Decision 2, amended) |
| `seasons` | `string[]` | `Object.keys(seasonData)` sorted descending — same ordering `App.tsx` derives today |

**Generated by**: `scripts/build-rankings.mjs`, written once after the per-season loop (same run
that deletes and repopulates `src/data/seasons/`), so it is always in sync with the season files
it lists.

**Relationships**: `Season Index` --(statically imports)--> `Season Ranking Record` (one edge per
season file) --(embeds)--> resolved `Postseason Result` stage (via `build-rankings.mjs`'s existing
reduction, unchanged).
