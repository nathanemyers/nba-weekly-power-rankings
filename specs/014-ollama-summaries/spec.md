# Feature Specification: Generate AI Summaries Through Ollama

**Feature Branch**: `014-ollama-summaries`

**Created**: 2026-10-24

**Status**: Withdrawn (2026-10-25). The maintainer chose to keep the Anthropic implementation with `claude-haiku-5-5` as the default model, on cost grounds. The research and local-model measurements are kept for reference.

**Input**: User description: "I want to update the AI summarization task to use ollama so that I can use a local model to perform these duties through ollama. Ideally I would also be able to ollama to use paid credits."

**Depends on**: `006-team-ai-summary`. This spec changes only which model service writes the summaries. What a summary is, when it is generated or regenerated, and how it is shown in the app all stay as 006 defines them.

## Clarifications

### Session 2026-10-24

- Q: Should Ollama replace the Anthropic provider or sit beside it? → A: Replace it. The Anthropic SDK dependency and the `ANTHROPIC_API_KEY` requirement are removed.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Generate summaries with a model running on the maintainer's machine (Priority: P1)

The maintainer runs the existing summary-generation step after a weekly scrape, and the summaries are written by a model running locally through Ollama. No paid account, API key or internet connection to a model provider is needed.

**Why this priority**: This is the core of the request. It removes the per-call cost and the external account from the weekly routine.

**Independent Test**: With Ollama running locally and a model downloaded, delete one active-season team's stored summary and run the generation step. A new summary appears that passes the same checks as before, and its record names the local model that wrote it.

**Acceptance Scenarios**:

1. **Given** Ollama is running locally with the chosen model available, **When** the maintainer runs the generation step for a season with teams that need summaries, **Then** each of those teams gets a summary written by that local model and stored with the same fields as before.
2. **Given** a summary from the local model breaks the existing rules (empty, more than one paragraph, or over 1,200 characters), **When** the run reaches that team, **Then** the summary is rejected, nothing is stored for that team, the failure is reported, and the run continues with the next team.
3. **Given** the maintainer wants a different local model, **When** they name it for the run, **Then** that model is used and recorded with each new summary.

---

### User Story 2 - Clear guidance when the local model is not ready (Priority: P1)

If Ollama is not running, or the chosen model has not been downloaded, the maintainer is told exactly what is missing before anything is changed.

**Why this priority**: Local setups fail in ways a hosted API does not. Without a clear message, the maintainer sees every team fail one by one.

**Independent Test**: Stop Ollama and run the generation step. The run stops at once with a message saying Ollama could not be reached, and no stored file changes. Repeat with Ollama running but a model name that is not downloaded: the message names the missing model and how to get it.

**Acceptance Scenarios**:

1. **Given** Ollama is not running, **When** the maintainer runs a step that needs to generate at least one summary, **Then** the run stops before generating anything, says the model service could not be reached, and leaves all stored summaries unchanged.
2. **Given** the named model is not available, **When** the run starts, **Then** it stops with a message naming the model and how to make it available.
3. **Given** nothing needs generating, **When** the maintainer runs the step without Ollama running, **Then** the run completes normally, because no model is needed.

---

### User Story 3 - Use Ollama's paid cloud models instead of local hardware (Priority: P2)

When the maintainer wants a larger model than their machine can run, or a faster backfill, they switch the same generation step to Ollama's paid cloud models and pay with their Ollama account's credits.

**Why this priority**: The request names this as "ideally". It matters for quality and speed, but local generation alone already delivers the main value.

**Independent Test**: With an Ollama account that has credits, configure the run for a cloud model and generate one team's summary. The summary is stored and records the cloud model's name. The account's credential does not appear in any committed file, the app bundle, or the deploy workflow.

**Acceptance Scenarios**:

1. **Given** the maintainer has an Ollama account with credits, **When** they select a cloud model for the run, **Then** summaries are generated by that model and the record names it.
2. **Given** a cloud model is selected but the account cannot be used (not signed in, credential missing or rejected, or no credits left), **When** the run starts generating, **Then** it stops with a message saying which of these applies and leaves stored summaries unchanged.
3. **Given** a cloud run is in progress, **When** the provider limits the request rate, **Then** the affected teams are reported as failed for this run and are picked up again on the next run, as today.

---

### Edge Cases

- Completed seasons that already have summaries written by the previous provider are never regenerated just because the provider changed. They stay locked exactly as 006 requires.
- An active-season summary from the previous provider is regenerated only when its source write-ups change, as today. A provider change alone does not trigger regeneration.
- A model that "thinks out loud" before answering: only the final answer may be stored. Any reasoning text is discarded before the summary checks run.
- A local model is much slower than a hosted one: a backfill of about 270 summaries may take a long time. An interrupted run must resume where it stopped, as today.
- A small local model may ignore instructions and add facts that are not in the write-ups. The existing rule that summaries use only the team's own write-ups still applies, and the instructions given to the model are unchanged in substance.
- A dry run (`--dry-run`) never contacts Ollama, locally or in the cloud.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The summary-generation step MUST generate summaries through Ollama, using a model running on the maintainer's machine by default.
- **FR-002**: The maintainer MUST be able to choose which model is used for a run without editing code. A sensible local default MUST apply when none is chosen.
- **FR-003**: The maintainer MUST be able to switch a run to Ollama's paid cloud models without editing code.
- **FR-004**: Every stored summary MUST keep recording the exact model that wrote it, so local, cloud and earlier summaries can be told apart.
- **FR-005**: Summaries from any model MUST pass the existing checks (non-empty, one paragraph, at most 1,200 characters) before they are stored. A summary that fails is not stored and the failure is reported.
- **FR-006**: The input sent to the model MUST remain limited to the team's own weekly write-ups for that season, as 006 requires.
- **FR-007**: The rules for when a summary is generated, skipped or locked MUST be unchanged. In particular, changing the provider or model MUST NOT cause any completed-season summary to be regenerated.
- **FR-008**: When the model service is unreachable, the chosen model is unavailable, or cloud credentials are missing, rejected or out of credit, the run MUST stop before changing any stored summary and MUST say which problem occurred and how to fix it.
- **FR-009**: Any credential for Ollama's paid service MUST come from the maintainer's environment or Ollama's own sign-in, and MUST NOT be committed, bundled into the site, or required by the deploy workflow.
- **FR-010**: A dry run MUST NOT contact any model service.
- **FR-011**: The project's documentation for the weekly refresh routine MUST describe how to run generation locally, how to choose a model, and how to use the paid cloud option.
- **FR-012**: The step MUST no longer require an Anthropic account or API key, and the Anthropic SDK MUST be removed from the project's dependencies.

### Key Entities

- **Stored summary** *(existing, from 006)*: Unchanged fields. The `model` field now holds an Ollama model name for new summaries; older entries keep the name of the model that wrote them.
- **Generation settings**: Chosen per run by the maintainer: which model, and whether it runs locally or in Ollama's cloud. Never stored in the repository.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A weekly active-season refresh (at most 30 summaries) can be completed with no paid account and no network access to a model provider.
- **SC-002**: Switching between a local model and a paid cloud model takes a single setting change and no code change.
- **SC-003**: After the change, 100% of completed-season summary files are byte-for-byte identical to before, unless the maintainer deliberately deletes an entry.
- **SC-004**: Every setup problem in User Story 2 and the account problems in User Story 3 produce a message that names the problem, and leave stored summaries unchanged.
- **SC-005**: No Ollama credential appears in the repository, the built site, or the deploy workflow.

## Assumptions

- **Ollama replaces Anthropic** (confirmed by the maintainer, see Clarifications). Summaries already written by Anthropic models stay as they are.
- "Paid credits" means Ollama's own paid cloud models, used through the maintainer's Ollama account, not another provider reached through Ollama.
- The maintainer installs Ollama and downloads models themselves. The project does not install or manage Ollama.
- The default local model is chosen during planning, balancing summary quality against what typical maintainer hardware can run.
- Summary quality from a local model may be lower than before. That is accepted; the existing checks are the quality gate, and the maintainer can switch to a larger or cloud model.
- The summary-generation step stays a manual, local step and does not run in CI, as today.
